Executive summary

The on-chain program is small (eight instructions, roughly 600 lines of Rust) and well constructed. Every account is constrained by seeds, owner, type or address, the admin bootstrap is bound to the program's upgrade authority, authority transfer is two-step, fee math is overflow-safe, and the freeze-plus-delegate escrow is applied atomically. I found no path for a third party to drain listed NFTs, steal fees, or take over the admin role through the program itself.

The material risk sits around the program rather than in it. The program is upgradeable, so whoever holds the upgrade authority can replace the code and sweep every frozen listing, and the mainnet deploy script hands both that authority and the config admin to a pasted address with no proof that anyone can sign for it. Those two items are rated Medium. Everything else is Low or Informational: defense-in-depth checks the program currently gets for free from SPL Token semantics, a leftover delegate approval after admin eject, treasury account hygiene, and operational hardening of the scripts.

1. Scope and method

Everything in the repository was read in full: the Anchor program (programs/grail-grove/src, all eight instruction handlers, state, errors, events, fee math and metadata validation), the three operational scripts (admin.ts, deploy-mainnet.ts, devnet-setup.ts), the IDL sync script, the Mocha integration suite (43 cases) and its helpers, Anchor.toml, both Cargo.toml files, Cargo.lock, package.json and .gitignore.

The review focused on the attack classes that matter for a Solana NFT escrow:

  • Missing or weak account validation: signer, owner, PDA seeds and bump, program-ID pinning, type cosplay, account substitution and duplicate-mutable accounts.
  • Privilege: admin bootstrap front-running, authority takeover, re-initialization, upgrade-authority exposure.
  • Asset safety: any way to move a listed NFT without a matching swap, to receive a listed NFT without surrendering one, to collect fees without delivering, or to brick a listing so the owner cannot recover it.
  • Token-program semantics: what SPL Token and Token Metadata permit on a frozen, delegated token account, verified against the upstream sources rather than from memory.
  • Arithmetic, rent and lamport flows; pause semantics; CPI signer-seed leakage.
  • Operational security of deployment, key handling and secrets.

Verification performed in this environment: the Rust unit tests compile and pass (8 of 8). The upstream SPL Token processor and Metaplex freeze and thaw processors were fetched and inspected to confirm the invariants the program depends on. The Anchor integration suite was not executed here because it needs a local validator with a mainnet clone of Token Metadata, which this container's network policy blocks. Mainnet RPC was also blocked, so on-chain state (collection, treasury, program) could not be inspected; see I-02.

2. System overview

A holder lists a Chimpion without giving up custody: the list instruction approves the per-mint Listing PDA as SPL delegate for one token, then the PDA calls Token Metadata's FreezeDelegatedAccount so the mint's master edition (the freeze authority) freezes the holder's token account. A taker calls swap with any other verified Chimpion: they pay a flat fee that is split between the treasury and the lister, the PDA thaws the listed account and delegate-transfers the NFT to the taker, and the taker transfers their NFT to the lister. delist (owner) and eject (admin) thaw and close. Admin is a Squads vault with pause, fee and treasury controls and a two-step handoff.

Security invariant the whole design rests on

While a listing exists, the listed token account is frozen and its delegate is the Listing PDA. I confirmed against the SPL Token processor that a frozen account rejects Transfer, Burn, Approve, Revoke and SetAuthority, and that CloseAccount requires a zero balance. Only the master edition PDA can thaw, and Token Metadata only signs that thaw when the current delegate signs (assert_signer(delegate) plus assert_delegated_tokens). The Listing PDA signs only inside delist, swap and eject, each of which closes the listing. So between list and one of those three, nobody can move, re-delegate, re-own or close the listed account. That invariant holds in the code as written.

4. Findings

Medium  M-01. Upgrade authority has unilateral control over every listed NFT

Anchor.toml (upgradeable = true), scripts/deploy-mainnet.ts steps 4 and 5, program-wide
Description
The program is deployed upgradeable and the upgrade authority is handed to the Squads vault. An upgrade can replace the program with code that signs as any Listing PDA and delegate-transfers every frozen, listed NFT to an arbitrary wallet in a single transaction per listing. Nothing in the program limits this, because by design the Listing PDA is the only key that can thaw and move a listed token. The config admin, by contrast, is well scoped: eject only ever returns the NFT to its owner and no admin instruction can redirect an NFT.
Impact
Compromise of the vault's signers (or a collusion at threshold) means total loss of all open listings. Users are told the swap is non-custodial, but in practice custody is "anyone who can upgrade the program".
Recommendation
  • Document the vault's member count and threshold publicly, and use a Squads time lock on the vault so an upgrade proposal is visible for a period during which listers can delist.
  • Publish a verifiable build (solana-verify / Anchor verified builds, see I-03) so the deployed bytecode can be matched to this reviewed commit.
  • Once the program has been live and stable, consider making it immutable (set the upgrade authority to none). The config admin still retains pause, fee and eject, which is enough for day-to-day operation.
  • Keep the open-listing count small relative to the collection by nudging listers to delist when idle (see I-01 on expiry).

Medium  M-02. Deploy script hands admin and upgrade authority to an unverified address, irreversibly

scripts/deploy-mainnet.ts lines 83, 159–167, 217–241, 265–278
Description
The --multisig flag is parsed as a public key and then used three times: as Config.authority inside initialize, as the IDL authority, and as the program upgrade authority with --skip-new-upgrade-authority-signer-check. The only sanity check is a warning if the key is on the ed25519 curve. The "verify" step compares the on-chain values back to the same command-line input, so a typo, a settings-account address pasted instead of the vault address, or a vault from the wrong Squads deployment all pass verification.
Impact
If the address is wrong, nobody can sign for it. Config.authority can only be changed by itself via propose_authority, so the program can never be paused, re-priced or unwound. The upgrade authority is lost with it, so the program also cannot be fixed. There is no recovery path short of abandoning the program ID, and any listings created in the meantime can only be closed by their owners via delist.
Recommendation
  • Before anything irreversible, prove control of the address: fetch the Squads multisig settings account the operator names, derive the vault PDA from it and the vault index, and require equality with --multisig. Better still, require the vault to have executed at least one transaction on mainnet (for example a 0 SOL transfer to itself) and check for it.
  • Make the config handoff recoverable: initialize with the deployer as authority, then run propose_authority(vault) and have the vault execute accept_authority. That exercises the vault's signing path before the upgrade authority is moved, and a bad address simply fails to accept. The script's current rationale ("deployer is never admin, not even briefly") trades a few minutes of deployer admin for an unrecoverable failure mode; with a dry run and a verified build the trade is worth making.
  • Only after the vault has accepted config authority, transfer the upgrade authority, and run solana program show plus pnpm admin show as the final check.

Low  L-01. Swap and list rely on SPL Token frozen-account semantics instead of explicit checks

swap.rs lines 66–72; list.rs lines 39, 64–70
Description
swap checks that lister_listed_token_account is the account recorded at list time and holds one token, but not that its owner is still lister or that its mint is listed_mint. list checks the owner's token account but, unlike swap's check on the offered mint, does not assert mint.supply == 1 && mint.decimals == 0. Both are safe today: a frozen token account cannot change owner or mint, and a Token Metadata edition account cannot exist for a mint that was not single-supply when the edition was created. The safety is inherited from two external programs rather than stated in this one.
Impact
None currently. The risk is latent: a future change to SPL Token semantics, a future instruction in this program that thaws without closing, or a Token-2022 variant would silently remove the protection.
Recommendation
Add the cheap explicit constraints: in swap, lister_listed_token_account.owner == lister.key() and .mint == listed_mint.key(); in list, mint.supply == 1 && mint.decimals == 0, and optionally mint.freeze_authority == Some(master_edition.key()) to fail with a clear error rather than a CPI error.

Low  L-02. Eject leaves a live SPL delegate approval on the owner's token account

eject.rs lines 14–18, 80–98
Description
After eject, the owner's token account is thawed and the listing closed, but the account still carries delegate = Listing PDA, delegated_amount = 1. The code comments acknowledge this and argue it is inert because no instruction can sign for a PDA whose listing account no longer exists. That reasoning is correct for the current code: the three signing instructions all require a live Listing whose token_account matches, and list re-approves anyway.
Impact
Wallets and security tools display the approval as an active third-party spend permission on the NFT, which will generate support load and distrust. It also sets a trap for future maintainers: if any later version adds an instruction in which the Listing PDA signs a token transfer without the listing.token_account binding, every previously ejected account becomes drainable.
Recommendation
The program cannot revoke on the owner's behalf. Surface the state in the web app after an eject with a one-click SPL Revoke, document it in the user-facing FAQ, and add a code comment on swap's lister_listed_token_account constraint noting that it is the control that keeps stale approvals inert.

Low  L-03. Treasury is not required to be a system-owned account; misconfiguration halts all swaps

initialize.rs lines 31–37; update_config.rs lines 25–31; swap.rs lines 137–148
Description
The only on-chain constraint on the treasury is "not the default key and has at least one lamport". The deploy script checks system ownership off-chain, but update_config accepts any funded account. If the admin sets the treasury to an executable account, a PDA of another program, or a token account, the system-program transfer in swap either fails (executable accounts cannot receive lamports) or sends fees somewhere they cannot be spent. Separately, if the treasury is a normal wallet that is later drained to zero, a swap whose treasury share is below the rent-exempt minimum for a zero-data account (890,880 lamports) fails the runtime rent check. At the default 0.02 SOL fee and 50% split the share is 10,000,000 lamports, so this only bites with fees under roughly 0.0018 SOL.
Impact
Admin-only, so not an exploit, but a plausible misconfiguration that stops every swap until corrected, and fees could be permanently stranded.
Recommendation
Add owner == system_program::ID to both treasury constraints and require lamports() >= Rent::minimum_balance(0). Keep the deploy-script check as well.

Low  L-04. Fee parameters change instantly and apply retroactively to open listings

update_config.rs; swap.rs lines 133–135; state.rs lines 8–10
Description
The admin can move swap_fee_lamports anywhere up to 1 SOL and treasury_bps anywhere up to 100% in one transaction. The lister's share is computed at swap time from the current config, so a lister who posted when the split was 50/50 may receive nothing if the split is 100/0 when a taker arrives. Takers are protected by max_fee_lamports, but only if the client sets it to the fee it displayed rather than a generous ceiling.
Impact
Trust and UX rather than theft: the admin is a multisig and the cap is 1 SOL. A 0.02 SOL to 1 SOL jump would still surprise anyone whose client passes u64::MAX as the max.
Recommendation
In the web app, pass exactly the quoted fee as max_fee_lamports. On-chain, consider either snapshotting treasury_bps into the Listing at list time, or a Squads time lock on config changes so listers can react.

Low  L-05. Helius API key is passed on child-process command lines

scripts/deploy-mainnet.ts lines 207–241; scripts/devnet-setup.ts line 333
Description
Both scripts build anchor deploy, anchor idl set-authority and solana program set-upgrade-authority command strings that embed the full RPC URL including ?api-key=…, and run them with execSync. The key is visible to any process on the machine via ps, lands in CI logs that echo commands, and the shell-splitting execSync path means an RPC URL containing shell metacharacters would be interpreted. Console output is correctly redacted; the subprocess argv is not.
Recommendation
Pass the RPC URL to the Solana tooling through its config file or environment (ANCHOR_PROVIDER_URL, solana config set --url in a temporary config dir) instead of argv, and use spawnSync with an argument array rather than a shell string.

Low  L-06. Admin CLI defaults to mainnet and the default Solana keypair

scripts/admin.ts lines 111–152
Description
With neither --cluster nor --rpc, the CLI targets api.mainnet-beta.solana.com, and without --keypair it signs with ~/.config/solana/id.json. A developer who forgets a flag while iterating on devnet sends a signed mainnet transaction. Today only initialize could succeed with a non-multisig key, and only from the deployer, but the default still points the sharp end at production.
Recommendation
Require --cluster or --rpc explicitly, and require --keypair whenever a transaction will be sent. Print a confirmation prompt when the resolved cluster is mainnet and --print is not set.

Info  I-01. Listings are open offers with no expiry or trait filter (adverse selection)

state.rs Listing; list.rs
A listing says "swap my Chimpion for any verified Chimpion". A rational taker always offers the least desirable one they hold, so listers should expect to receive the floor, and the fee share is their compensation. created_at is recorded but never used; listings never expire, so forgotten listings remain filled-at-floor targets indefinitely (and enlarge the exposure described in M-01). Consider an optional expiry checked in swap, and make the "any Chimpion" semantics prominent in the UI.

Info  I-02. Unverified mainnet assumptions: collection token standard and freeze authority

deploy-mainnet.ts lines 40–41; metadata.rs lines 21–24
The program only works for legacy NonFungible (or pre-standard) NFTs whose mint freeze authority is the master edition PDA. Mainnet RPC was blocked from this environment, so I could not confirm that the Chimpions collection 2k8iNEAB… matches, that the treasury Df7VuBka… is a system wallet, or whether the program ID is already deployed. Before mainnet, confirm a sample of Chimpions have token_standard None or NonFungible and freeze_authority == master_edition; otherwise list fails for every token. The Anchor test suite already covers the pNFT rejection path for the offered side only.

Info  I-03. No verifiable-build step; declared and resolved Anchor versions differ

deploy-mainnet.ts; programs/grail-grove/Cargo.toml; Cargo.lock
The deploy script records the binary's SHA-256 but nothing ties it to a reproducible build of a public commit. Cargo.toml declares anchor-lang = "0.32.1" while Cargo.lock resolves 0.32.2. Pin exact versions (=0.32.2), build with solana-verify build or anchor build --verifiable, and upload the verification PDA so explorers show the program as verified. This is the main mitigation for the trust gap in M-01.

Info  I-04. active_listings uses saturating subtraction

delist.rs line 93; swap.rs line 216; eject.rs line 101
saturating_sub(1) hides any future accounting bug (a double decrement would read as zero rather than fail). The counter is informational, so this is a maintainability note: checked_sub with an error, matching the checked_add in list, would surface drift immediately.

Info  I-05. Misleading error code on eject owner mismatch

eject.rs line 34
has_one = owner @ GrailGroveError::TokenAccountMismatch reports a token-account error when the owner account does not match the listing. Introduce a dedicated OwnerMismatch error so the admin CLI's failure messages are accurate.

Info  I-06. Test coverage gaps

tests/grail_grove.test.ts
The 43 integration cases cover the main paths and most negative cases well. Missing cases worth adding, each of which should fail today for the right reason:
  • Listing a pNFT (only the offered-side pNFT rejection is tested).
  • An NFT whose collection.key is correct but verified is false (the existing "outside the collection" test uses no collection at all).
  • Swap with a substituted lister_listed_token_account or listed_master_edition.
  • Swap where the taker's ATA for the listed mint already exists, and where the lister's ATA for the offered mint already exists.
  • After eject: owner transfers the NFT out and the new holder lists it (exercises the stale-delegate reasoning in L-02).
  • propose_authority(Pubkey::default()) as a cancellation, followed by a rejected accept.
  • An NFT whose mint freeze authority is not the master edition (list should fail cleanly).

5. What the program does well

  • Admin bootstrap cannot be front-run. initialize requires the payer to be the program's upgrade authority and binds the ProgramData account to the program through programdata_address(), the pattern Anchor recommends.
  • Two-step authority handoff with a non-default check on accept, so a mistyped proposal cannot brick admin.
  • Every PDA is seed-checked with a stored canonical bump; Metaplex PDAs use seeds::program plus an owner check; the Token Metadata program is pinned by address and Token, ATA and System are typed.
  • Collection gating is correct: metadata PDA derived from the mint, mint equality, legacy token standard only, and collection.verified && key == config.collection.
  • Escrow is atomic: approve and freeze happen in the same instruction; thaw, delegate transfer and counter-transfer happen in the same instruction; close refunds rent to the right party in all three exit paths.
  • Fee math is done in u128 with checked operations, rounding dust goes to the lister, the fee is capped at 1 SOL and bps at 10,000, and the taker has a slippage guard.
  • Pause is one-directional: it blocks new listings and swaps but never traps assets.
  • Deployment discipline: dry-run by default, mainnet genesis check, program-ID and keypair agreement, treasury ownership check, post-deploy verification, redacted logs, and secrets kept out of git.
  • overflow-checks = true in the release profile; Boxed accounts to keep the stack small; 43 integration tests and 8 passing unit tests.

6. Recommended order of work

  1. Decide the upgrade-authority posture (M-01): time lock and published threshold now, verifiable build before launch (I-03), immutability as a later milestone.
  2. Rework the deploy handoff so the vault proves it can sign before anything irreversible happens (M-02).
  3. Add the defense-in-depth constraints (L-01, L-03) and the error-code and counter cleanups (I-04, I-05). These are a few lines each and do not change behavior for valid transactions.
  4. Client work: pass the quoted fee as max_fee_lamports (L-04), show and offer to revoke stale approvals after eject (L-02), make the "any Chimpion" semantics explicit (I-01).
  5. Script hardening (L-05, L-06) and the additional tests (I-06).
  6. Confirm the mainnet assumptions in I-02 against live data before deploying.
